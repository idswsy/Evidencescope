# 09 · 上位机实时波形显示

> 状态：**已实现（2026-10-06），真机验证待做** · 2026-10-06
>
> 关联：[ADR-014](06-decisions.md)（屏幕采用被动帧模型）、[04-performance.md](04-performance.md)（吞吐上限）

---

## 1 问题

上位机 GUI 的波形是**按一次采一次**：用户点一次「采集」，界面更新一次。而本机那个参考实现（上游开源工程）的屏幕是持续刷新的 —— 于是"看起来像示波器"这件事，本工程反而落后了。

用户提出的方案是：去掉板载显示、专注上位机，并把波形改成实时更新。

---

## 2 对原方案的三处修订

原方案里有三条经核实不成立，实现前必须纠正，否则会把工作量花在错的地方。

### 2.1 「内存充足就能实时更新」——瓶颈不是内存，是链路带宽

| 项 | 值 |
|---|---|
| 链路 921600 8N1 | 92.16 KB/s |
| 每样点 RAW16 | 2 B → **46 080 样点/s** |
| 采样率 | **857 142 样点/s** |
| 实时原始传输所占比例 | **5.4%** |

一次 4096 点采集的载荷 8192 B，加分片头与帧头约 8288 B，**传输耗时 90 ms → 11 fps**。这个数字与内存无关。

### 2.2 「像上游一样实时」与「保留 857 kSPS」在原方案下互斥

上游那台"像示波器"的原因不是内存充足，而是**采样率低**：`ADC_SAMPLETIME_239CYCLES_5` → 21 µs/样点 → **47.6 kSPS**，300 点即 6.3 ms 窗口，且为自由连续采集。

本工程 857 kSPS × 1024 点只有 1.19 ms 窗口 —— 同一个 1 kHz 信号仅能看到 1.2 个周期。**窗口长度由采样率与点数共同决定，不由内存决定。**

用户已确认保留 857 kSPS 与 4096 点，因此窗口固定为 4.78 ms；可改变的只有帧率。

### 2.3 「PCB 未引排针导致引脚不便使用」——不构成改动理由

固件当前使用的引脚与底板 PCB 走线逐条一致（TFT 用 PA5/PA7/PB5–PB8，按键 PB13–PB15，编码器 PB3/PB4/PB9，LED PC14/PC15，测频 PA6，函数发生器 PA2）。**「适配这块 PCB」已经满足。**

另：不驱动屏幕 **不释放这些引脚** —— 它们仍被 PCB 布到屏座。若目标是启用未被走线占用的引脚（PB10/PB11/PB12/PA0/PA1/PA4/PA8–PA11 等），那需要飞线，而排针缺失恰恰使其更难。**这是两件独立的事。**

## 3 可行性依据

两条经核实的余量，使「保留 857 kSPS 与 4096 点」的前提下仍可显著提高帧率。

### 3.1 波特率余量 2 倍

- 设备波特率由 `LINK_BAUD` 宏决定（默认 921600，`Core/Src/usart.c`）
- F103 的 USART1 挂 APB2 = 72 MHz；**2 Mbps 时 USARTDIV = 2.25（= 2 + 4/16，可精确表示）→ BRR = 0x24 = 36，零误差**
- CH340 系列（G/C/E）按数据手册支持至 2 Mbps
- 上位机 `transport-serial` 的 `SerialDevice::open(port, baud, timeout)` 本就接受波特率参数，只需在常量表中增加一档

### 3.2 PACK12 已实现（2026-10-06）

PACK12 为每样点 1.5 B（2 样点 → 3 B），**载荷减少 25%**。编解码函数 `proto_pack12_pair` / `proto_unpack12_pair` 在 `proto/protocol.h`（两端跑同一份黄金向量）。

- 设备：`cmd_read_buffer` 支持 `FMT_PACK12`，分片头的 `format` 如实回显请求值；奇数 `count` 时末样点与 `0` 凑对（约定见 `docs/03-protocol.md` §6.4）。
- 主机：`scope-core` 的 `acquire` 请求 PACK12，并按**分片头回显的 `format`** 解码（不是按请求值）——设备有权回别的格式，按请求值解会把两种字节当同一种读。
- 回归：`firmware/tests/test_proto_task.c` 的 PACK12 往返组（与 `acq_sample` 逐点相等）+ 主机端 `decode_chunk_samples` 单测 + scope-mcp 的「按回显格式解码」端到端测试。

> ~~**遗留缺陷（不在本次范围）**：`DEV_CAPS` 仍宣称 `CAP_FMT_MINMAX`……~~
> **2026-10-10 已修（`4e165e6`）**：`DEV_CAPS` 摘掉了 `CAP_FMT_MINMAX` 与 `CAP_TRIG_SOFT`
> 两个做不到的能力位（`cmd_read_buffer` 对 MINMAX 回 `ERR_UNSUPPORTED`、
> `cmd_force_trigger` 恒回 `ERR_UNSUPPORTED`）。`proto_task.c` 上方那段
> 「不要声明做不到的能力」的注释（针对 `CAP_CH_DUAL` / `CAP_COUPLING_AC`）**现已守住**，
> 并在 `test_proto_task.c` 的 GET_INFO 组补了负向断言防回归。
> 完整对照见 `docs/03-protocol.md` §11.2。
>
> ⚠ **仅真机侧已修**：主机侧模拟器（`host/crates/sim/src/device.rs`）的 `GET_INFO.caps`
> 仍是旧的一套（含 `CAP_TRIG_SOFT` / `CAP_FMT_MINMAX` / `CAP_COUPLING_AC` /
> I2C 场景下的 `CAP_CH_DUAL`），与真机不一致 —— 见 `docs/03-protocol.md` §11.4。

## 4 方案

四步，每步独立上板可验。

### 4.1 第一步：GUI 连续刷新（零固件改动）

GUI 增加「连续刷新」开关。打开后 worker 循环执行「采集一帧 → 上屏 → 立即下一帧」，复用现有 `capture -n 4096`。

- 预期 **11 fps**
- 关闭开关即回到当前的单次采集行为
- 同时提供 `--continuous` 命令行入口，便于不上窗口时验证

选择先做它的理由：它是唯一零风险的部分，且第二、三步完成后**这段代码无需改动**，只是变快。

### 4.2 第二步：链路提速至 2 Mbps

| 侧 | 改动 |
|---|---|
| 设备 | `Core/Src/usart.c` 的 `BaudRate` |
| 上位机 | `transport-serial` 波特率常量表增加 2000000 |

**默认仍为 921600**，2 Mbps 作为可选项（`--baud 2000000`）。实测确认稳定后再考虑改默认值。

- 预期 **24 fps**
- 本步必须**单独验证**：它决定第三步是否值得做
- 判据：`ping` 10/10；连续 `capture` 50 次；`status` 的 `rx_crc_err` 与 `rx_dropped` 全程为 0

### 4.3 第三步：实现 PACK12（已完成 2026-10-06）

| 侧 | 改动 | 状态 |
|---|---|---|
| 设备 | `cmd_read_buffer` 支持 `FMT_PACK12`；分片头的 `format` 字段如实填写 | ✅ |
| 上位机 | `scope-core` 解包 + `acquire` 请求该格式 | ✅ |
| 协议 | `docs/03-protocol.md`；黄金向量沿用既有 7 组（含 `0x000`/`0xFFF` 两端极值） | ✅ |

本仓纪律：**改协议 = 改四处（文档 / `.h` / `.rs` / 向量）+ 一次提交**。

- 预期 **32 fps**（帧率数字待真机 + 2 Mbps 实测）
- 硬判据：**同一份采集，PACK12 解出的样点与 RAW16 逐点相同** —— 已由固件 PACK12 往返组、主机 `decode_chunk_samples` 单测、scope-mcp 端到端回归钉住

### 4.4 第四步：冻结屏幕代码（已完成 2026-10-06）

`Hardware/src/display.c` 从 Keil 工程移除（文件保留，无编译开关）。

- 释放约 **450 B** RAM（`display.c` 的 `.bss` 实测 448 B）
- 板载屏幕不再驱动；`SCOPE_LOCAL_UI` 维持 0 不变

## 5 预期结果

| 阶段 | 帧率 | 窗口 | 采样率 | 单次点数 |
|---|---|---|---|---|
| 现状 | 按需 | 4.78 ms | 857 kSPS | 4096 |
| + 第一步 | ~11 fps | 4.78 ms | 857 kSPS | 4096 |
| + 第二步 | **~24 fps** | 4.78 ms | 857 kSPS | 4096 |
| + 第三步 | **~32 fps** | 4.78 ms | 857 kSPS | 4096 |

**采样率、单次点数、窗口长度在三步中均不变。**

> ⚠ 默认 921600 下即为 **~13–15 fps**（PACK12 恒开、非可选档）；上表中 ~24 / ~32 fps 是**启用 2 Mbps 时**的数字，2 Mbps 才是可选档。

## 6 明确不做

| 项 | 理由 |
|---|---|
| 修改采集链 | 857 kSPS / 4096 点 / 触发 / 预触发均为已确认的约束 |
| 改动硬件或引脚 | 固件已与 PCB 走线一致 |
| 实现 `STREAMING` 流模式 | 带宽不变则帧率不变，与连续刷新等价而成本更高 |
| 为「腾出引脚」拔出屏幕飞线 | 与本次目标无关 |
| 删除屏幕代码 | 冻结而非删除，保留恢复的可能 |

---

## 7 风险

| 风险 | 发现方式 | 处置 |
|---|---|---|
| **2 Mbps 在杜邦线上不可靠** | 第二步的判据（连续 50 次 capture，`rx_crc_err` 为 0） | 退回 921600，仍有 11 fps |
| 提速后收包环容差变小（1 KB 仅够 5 ms） | 同上；`rx_dropped` 计数 | 必要时把 `LINK_RX_RING` 加大 |
| PACK12 解包与 RAW16 不一致 | 已由三处自动化测试钉住（固件往返 / 主机单测 / MCP 端到端），真机剩 CSV 逐点对比 | 视为未完成 |
| 连续刷新挤占 GUI 响应 | 人工使用 | 开关默认关闭 |

## 8 连续刷新的行为定义

为免实现时各自理解不同，此处定死。

| 项 | 定义 |
|---|---|
| 点数与采样率 | **沿用界面上当前的设置**，不另设一套 |
| 触发配置 | 沿用设备当前配置；AUTO 模式下无信号时每帧约 200 ms（约 5 fps），有信号时按触发速度 |
| 画面 | **每帧替换**。不做余晖、不做历史叠加 —— 那需要另一个存储与另一套渲染，与本次目标无关 |
| 起停 | 开关默认**关闭**；关闭即立即停止循环并恢复到「按需采集」 |
| 出错 | 任一次采集失败即停止循环并在状态栏给出原因，不静默重试 |

> ⚠ **AUTO 模式下的 5 fps 是已知的下限。** 测量直流或无信号时，设备要等满 200 ms 的 auto 超时才返回一帧。这是协议既有语义（见 `App/acq.h` 的 `ACQ_AUTO_TIMEOUT_MS`），本方案不改动它。要看连续波形需接一个会变化的信号。
